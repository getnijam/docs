Nijam is built to run in CI. You don't pass commit, branch, PR, or author by hand — the reporter
**detects them automatically** from your CI provider, so each run lands in history with full context.

## What's detected

Commit, branch, PR number, **CI run id**, CI run URL, and the **git author** (email + name). Resolution
order, per field:

1. CI-specific environment variables (see below)
2. Generic `GIT_*` / `BRANCH` / `COMMIT_SHA` variables
3. A `git log` / `git rev-parse` shell-out
4. Empty (branch is left unset → the dashboard shows "No Branch Info")

<Aside type="note">
Author **email** isn't exposed by every provider. GitHub, CircleCI, and Bitbucket don't surface a
commit-author email, so the reporter falls back to `git log -1` and then `git config user.email`.
</Aside>

## Supported providers

<Tabs>
<TabItem label="GitHub Actions">

Detected from `GITHUB_SHA`, `GITHUB_REF_NAME`, `GITHUB_HEAD_REF`, `GITHUB_RUN_ID`,
`GITHUB_REPOSITORY`, `GITHUB_SERVER_URL`.

```yaml title=".github/workflows/e2e.yml"
name: e2e
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test
        env:
          NIJAM_API_KEY: ${{ secrets.NIJAM_API_KEY }}
```

</TabItem>
<TabItem label="GitLab CI">

Detected from `CI_COMMIT_SHA`, `CI_COMMIT_REF_NAME`, `CI_PIPELINE_ID`, `CI_MERGE_REQUEST_IID`,
`GITLAB_USER_EMAIL`, `GITLAB_USER_NAME`, `CI_COMMIT_AUTHOR`.

```yaml title=".gitlab-ci.yml"
e2e:
  image: mcr.microsoft.com/playwright:latest
  script:
    - npm ci
    - npx playwright test
  variables:
    NIJAM_API_KEY: $NIJAM_API_KEY
```

</TabItem>
<TabItem label="CircleCI">

Detected from `CIRCLE_SHA1`, `CIRCLE_BRANCH`, `CIRCLE_BUILD_NUM`, `CIRCLE_PULL_REQUEST`,
`CIRCLE_BUILD_URL`.

```yaml title=".circleci/config.yml"
jobs:
  e2e:
    docker: [{ image: mcr.microsoft.com/playwright:latest }]
    steps:
      - checkout
      - run: npm ci
      - run: npx playwright test
        environment:
          NIJAM_API_KEY: $NIJAM_API_KEY
```

</TabItem>

Detected from `BITBUCKET_COMMIT`, `BITBUCKET_BRANCH`, `BITBUCKET_PR_ID`, `BITBUCKET_BUILD_NUMBER`,

## Sharded runs

When you split tests across machines with Playwright's `--shard=i/N`, **each shard is a separate
process** and they don't talk to each other. Nijam clubs them into **one run** server-side (they share
the CI run id), and a failure in any shard marks that run **Failing** right away.

Because no single shard knows when the others finish, **each shard only streams its results — it does not
finalize the run.** You add **one final step, after the whole matrix**, that tells Nijam to mark the run
complete (which is when the Slack notification fires). Until then the run shows **running / failing** live.

<Aside type="caution">
If you shard, this completion step is **required** — without it a sharded run never reaches a final
status. As a safety net, Nijam auto-marks any run with **no activity for over an hour** as **Canceled**,
so a missing step never leaves a run stuck on "Running".
</Aside>

The step is a single HTTP call needing your **API key**, **project id**, and the **CI run id** — and it
must run in the **same pipeline/workflow** as the shards (so the run id matches what they sent):

<Tabs>
<TabItem label="GitHub Actions">

```yaml title=".github/workflows/e2e.yml"
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test --shard=${{ matrix.shard }}/4
        env:
          NIJAM_API_KEY: ${{ secrets.NIJAM_API_KEY }}

  nijam-complete:
    needs: [test]        # run after every shard
    if: always()         # complete even if some shards failed
    runs-on: ubuntu-latest
    steps:
      - run: |
          curl -sf -X POST "https://api.nijam.dev/v1/runs/complete" \
            -H "Authorization: Bearer ${{ secrets.NIJAM_API_KEY }}" \
            -H "Content-Type: application/json" \
            -d "{\"projectId\":\"<your-project-id>\",\"ciRunId\":\"$GITHUB_RUN_ID\",\"ciRunAttempt\":\"$GITHUB_RUN_ATTEMPT\"}"
```

</TabItem>
<TabItem label="GitLab CI">

```yaml title=".gitlab-ci.yml"
e2e:
  parallel: 4
  image: mcr.microsoft.com/playwright:latest
  script:
    - npm ci
    - npx playwright test --shard=$CI_NODE_INDEX/$CI_NODE_TOTAL
  variables:
    NIJAM_API_KEY: $NIJAM_API_KEY

nijam-complete:
  needs: [e2e]
  when: always
  script:
    - >
      curl -sf -X POST "https://api.nijam.dev/v1/runs/complete"
      -H "Authorization: Bearer $NIJAM_API_KEY"
      -H "Content-Type: application/json"
      -d "{\"projectId\":\"<your-project-id>\",\"ciRunId\":\"$CI_PIPELINE_ID\"}"
```

</TabItem>
</Tabs>

The **`ciRunId` must equal the value the shards sent** — the same one the reporter detects
(`GITHUB_RUN_ID`, `CI_PIPELINE_ID`, …), which is shared across every job in the run. On providers whose
CI run id is *job-level* (e.g. CircleCI's `CIRCLE_BUILD_NUM`), pass the shared
workflow id through to the final step instead. Non-sharded runs need none of this — the reporter
finalizes them itself.

## Other CI systems

On a provider not listed above, set the **generic** variables and the reporter picks them up:

| Variable     | Maps to       |
| ------------ | ------------- |
| `COMMIT_SHA` | commit        |
| `BRANCH`     | branch        |
| `CI_RUN_ID`  | CI run id     |
| `CI_URL`     | CI run URL    |

If none are set, the reporter still falls back to `git`, so local runs are attributed too. The full
variable list lives in the [CI variables reference](/reference/ci-variables/).

## What you need to push runs

To send runs and reports to Nijam, the reporter needs **two** things — set both in
`playwright.config.ts`:

- **`projectId`** — which project to push to. Not a secret; it just identifies the project.
- **`apiKey`** — the only **secret**. Store it as `NIJAM_API_KEY` in your CI secrets and reference it via
  `process.env.NIJAM_API_KEY`.

Everything else — commit, branch, PR, CI link, author — is detected automatically.
